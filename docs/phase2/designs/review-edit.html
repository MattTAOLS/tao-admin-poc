B. The sharper page viewer

Opened from a source link, a finding crop, or the crop in the Edit dialog.
7The fix is in how page images are rendered, not in extraction. Today every page is rendered once at 110 dpi (PAGE_DPI = 110 in api/app/main.py, pdf.render_page in api/app/pdf.py) and the browser stretches that image when you zoom, so 200% is blurry. Moneda pages make it worse: they are 1,440 × 1,113 pt (20 × 15.5 in, a spreadsheet printed to one sheet), so the type is small on the page to begin with. The new viewer asks for an image at the resolution the zoom needs: the whole page at about 150 dpi for Fit and 100%, and only the visible area at 300 dpi (200%) or 600 dpi (400%). Each image is rendered on first request and cached. Extraction, its speed and its output stay exactly as they are.

8Zoom steps and Zoom to value. Steps become Fit, 100%, 200%, 400% (today Fit, 100%, 150%, 200%). Zoom to value jumps to 400% and centres the outlined cell, so the exact number fills the middle of the view. When the viewer opens from a value or a finding it starts at 200% centred on that cell, not at Fit.
9Magnifier. When on, a round lens follows the pointer (or sits on the outlined cell when using the keyboard) and shows that spot at twice the current zoom, read from the next sharper image. It is off by default and the choice is remembered per browser.
10No fading. Today the outline is filled with a tinted colour blended over the number (.rv-mark uses a fill with mix-blend-mode: multiply), which washes out the digits it is meant to point at. The new outline is a 2 px purple line drawn outside the cell with no fill, so the number keeps full contrast. Finding outlines keep red, source outlines purple.

11What changes in the code (for the build, not this design). (a) The page image route takes a resolution and an optional area, e.g. /uploads/{id}/pages/13.png?dpi=600&clip=x0,y0,x1,y1 (PDF points), with dpi limited to 150, 300 and 600; renders stay locked and atomic as today. A whole Moneda page at 600 dpi would be 12,000 × 9,275 px, which is why 200% and 400% fetch the visible area only. (b) The viewer and crops stop assuming 110 dpi (PX_PER_PT = 110 / 72 in PageImage.tsx) and work out the scale from the image's pixel size and the page size in points, so outlines stay on the right cell at every resolution. (c) Finding-card crops request the area around the outlined cells at 300 dpi. The alternative is vector rendering in the browser (pdf.js): sharp at any zoom, but it sends the PDF itself to the browser and adds a large library; see open questions.

What happens when you correct
  • Version 2 of this report is created with the new value. Version 1 stays in the Reports library as Replaced, with its numbers unchanged.
  • The rules re-run on version 2. If a block finding opens, nothing is published: version 2 goes to the Approval queue as Needs review, and the dialog says so.
  • If no block finding opens, version 2 is published straight away, the program roll-up regenerates, and partner portals show the corrected numbers.
  • One Reports audit entry for the correction, one for the re-publish.
13A correction works like today's corrected re-issue, without a new PDF upload: the library shows version 2 as Published with a Corrected tag and version 1 as Replaced, each linking to the other. Partners see the correction in their Notifications (D7) and a "Corrected" marker on the deal page for that period.
